## Blocked-port test

The test created the bridge with STP disabled, then issued:

```text
bridge link set dev ethernet1 state 4
```

The recorded kernel sequence was:

```text
[134.013739] br1: port 3(ethernet1) entered blocking state
[134.013763] br1: port 3(ethernet1) entered forwarding state
```

The capture then recorded 20 broadcast frames on that port, matching its
actual forwarding state. This is expected bridge behavior for the requested
configuration. `br_set_port_state()` calls `br_port_state_selection()`;
`br_make_forwarding()` returns a designated blocking port to forwarding when
`BR_NO_STP` is in effect. Source: `net/bridge/br_netlink.c:915`,
`net/bridge/br_stp.c:459` in the tested kernel tree.

The test must establish userspace-managed STP before manually setting blocking,
then read back state 4 before transmitting. An administratively disabled-port
test would exercise a different state and should be named separately. Merely
turning on kernel-managed STP does not authorize manual state changes: that
path returns `EBUSY`. The tested kernel supports an explicit userspace STP
mode, but the installed iproute2 utility's support must be checked before
choosing the configuration mechanism.

## Two independent mv88e6xxx statistics bugs

### Wrong MIB snapshot port encoding

`mv88e6171_ops.stats_snapshot` selects `mv88e6320_g1_stats_snapshot()`. That
function encodes `(port + 1) << 5`. The live device instead behaves as though
all these requests select physical port 0, `ethernet1`.

A controlled follow-up used the existing booted board over UART and ordinary
host pings; no kernel changes were applied:

| Stimulus | Packet evidence | Hardware MIB result |
| --- | --- | --- |
| Five IPv4 pings through ethernet3 (physical port 2) | Five replies; only ethernet3 software RX/TX counters advanced | `in_unicast` and `out_unicast` unchanged on every queried port |
| Five IPv6 pings through ethernet1 (physical port 0) | Five replies | Every port reported the same `in_unicast +5`, `out_unicast +6` |

Software RX/TX increments include neighbor discovery and background traffic;
they are included as path evidence rather than exact ping-packet assertions.
The extra transmitted unicast in the second probe is also outside the five
required ping replies. The decisive observation is that *all four* MIB views
changed identically with traffic on physical port 0.

The callback should use `mv88e6xxx_g1_stats_snapshot()` for this chip. Local
history supports the diagnosis: before commit `a605a0fe7115` (2016), only the
6320 and 6352 families received the shifted encoding. 6171 is family 6351.
The refactoring assigned it the shifted callback.

### Counter count/layout mismatch

The tested kernel has these inconsistent declarations for 6171:

- `stats_get_sset_count` and `stats_get_strings`: 6095-style BANK0 plus PORT.
- The chip information's `stats_type`: BANK0 plus BANK1.
- Collection filters entries using that `stats_type` bitmap.

Counting the actual source entries gives:

| Path | Base statistics | ATU/VTU software statistics | Driver total |
| --- | ---: | ---: | ---: |
| Advertised/named | 30 BANK0 + 3 PORT | 5 | 38 |
| Written | 30 BANK0 + 26 BANK1 | 5 | 61 |

These are the driver portion; the DSA wrapper also prefixes its own software
counters. The extra 23 `u64` writes exceed the driver's advertised array size.
The ioctl core sizes its allocation from the advertised count. This is an
out-of-bounds write relative to the requested buffer, although this analysis
does not establish that unrelated memory was corrupted on this board.

The wrong layout also explains why named ATU/VTU counters misleadingly match
hardware packet counters in the logs: their names index BANK1 values that the
6095-style reader interprets as BANK0 registers. Consequently the logged
`atu_full_violation`, `atu_miss_violation` and VTU counters cannot currently
settle the MAC-learning diagnosis.

For 6171, set `stats_type` to `STATS_TYPE_BANK0 | STATS_TYPE_PORT` to match
its count/string/read operations. Commit `5595e3613ea7` (2024) introduced the
bitmap and switched the collection filter to it; `9a4eef6bf2be` subsequently
centralized the same check. Both are present in the tested build.

Counter queries were stopped after identifying the size mismatch. Correct
both defects, rebuild and reboot before interpreting more driver statistics.

Two proposed patches are saved in
`/home/florian/dsa-test-analysis/ea4500-20261024/`:

- `6171-stats-layout.patch`

They pass `git apply --check` against the exact Buildroot kernel tree and have

## MAC learning

The failing source is `00:11:20:30:00:1c`, the fifth address in the step-7
sequence sent through host `enxf8e43ba6b140` / board `ethernet3`.

`mac-learning/captures/0003/` proves it appears once in that host's outbound
pcap and once in the intended peer's inbound pcap. All three streams contain
128 unique source MACs and each peer receives 128 packets. The missing address
is absent from the raw UART dump too, so this is not simply a Python FDB-parser
omission. The original traffic backend's exact stepping sequence was verified.

One-shot transmission and one FDB dump do not identify the underlying reason.
A repeat should be done after fixing the counter path, on a fresh boot:

1. Send exactly the missing source again, allow bounded convergence and read
   back the FDB repeatedly. Record whether it becomes learned.
2. Repeat the same 384-address set with multiple transmissions per source,
   checking the source distribution in pcaps rather than only total counts.
3. Record valid ATU full/member/miss counters before and after; vary the source
   set or hash mode only if needed to identify a repeatable bucket collision.
4. If a MAC remains absent, add it statically and test forwarding to it, then
   compare hardware `self` dumps against bridge `master` entries.

There is currently no basis to call this a general networking-stack packet-loss
bug, or to dismiss the missing hardware entry as harmless. The learning test
should retain the failure until the repeat isolates its cause.

## Other diagnostics

The UART log includes `hw VLAN 1 already used ... in br0/br1` while different
bridges use the default VLAN 1. The driver explicitly returns `EOPNOTSUPP` for
that offload conflict. The corresponding IP/packet-isolation checks passed.
These messages identify an offload/configuration limitation and motivate
explicit offload validation; they are not evidence that the captured forwarding
assertions failed.

The boot also reports mwl8k RF_ANTENNA errors. These concern wireless firmware
initialization, independently of the four wired-switch test failures.
